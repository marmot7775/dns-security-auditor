What is DMARCbis?

DMARCbis is the IETF's update to the DMARC email authentication standard. The draft (version 41) was approved by the IESG in 2025 and is now in the RFC Editor Queue, with publication as a Proposed Standard expected in 2026. When published, DMARCbis will obsolete RFC 7489 (published in 2015 as an Informational RFC), replacing it as the authoritative DMARC specification. That status change matters: it signals that DMARC is moving from an experimental protocol to a formal standard with stronger expectations for vendor compliance.

The name stands for "DMARC bis" (Latin for "twice" or "again"). It is the second iteration of the specification, and it also obsoletes RFC 9091, which defined Public Suffix Domain DMARC policies.

RFC 9091 (published in 2021) was an experimental standard that defined how public suffix domains could publish DMARC policies. DMARCbis incorporates RFC 9091's goals through the psd= tag while providing a more robust mechanism via the DNS tree walk. With DMARCbis, RFC 9091 is no longer needed and is formally obsoleted.

DMARCbis refines and clarifies existing DMARC behavior rather than replacing it wholesale. It uses the same record format (v=DMARC1), the same authentication model (SPF + DKIM + alignment), and existing DMARC records continue to work without modification. The most significant refinement is in how organizational domains are discovered. DMARCbis moves from the Public Suffix List to a DNS-based tree walk method.

The update addresses problems that surfaced over a decade of real-world DMARC deployment:

  • Receivers parsed records inconsistently
  • The percentage-based rollout tag was unreliable
  • Non-existent subdomains had no dedicated protection
  • Organizational domain boundaries depended entirely on the Public Suffix List, a manually-maintained external file that different receivers updated on different schedules

Records that relied on lenient parsing or deprecated features will need attention as receivers adopt the stricter rules.

Three-Document Split

RFC 7489 defined DMARC as a single document covering the core protocol, aggregate reporting, and failure reporting. DMARCbis splits the specification into three separate RFCs:

  • Core specification (draft-ietf-dmarc-dmarcbis), covering protocol mechanics, policy discovery, and identifier alignment
  • Aggregate reporting (draft-ietf-dmarc-aggregate-reporting), covering the rua= report format and delivery
  • Failure reporting (draft-ietf-dmarc-failure-reporting), covering the ruf= forensic report format and delivery

Separating concerns allows each specification to be updated independently. It also makes implementation clearer for different audiences: domain owners primarily need the core spec, while report processors can focus on the reporting documents without tracking unrelated protocol changes.

Why DMARCbis?

DMARC was published in 2015 as an Informational RFC. It worked, mostly, but a decade of deployment exposed real problems that could not be fixed with implementation guidance alone. The IETF working group spent several years working through these issues. Here is what they were solving.

Subdomain spoofing had no answer. RFC 7489 let you set a policy for your domain and a subdomain policy with sp=. But attackers learned to spoof from subdomains that do not exist in DNS, like secure-login.yourbank.com. There was no tag to address this. DMARCbis adds np= to let domain owners set a policy specifically for non-existent subdomains.

The Public Suffix List was a single point of fragility. DMARC needed to know where one organization's domain ends and the public suffix begins. It relied on the PSL, a community-maintained text file hosted on GitHub. Different receivers updated their copy on different schedules. A new TLD could go weeks without being recognized.

DMARCbis removes reliance on the Public Suffix List for organizational domain discovery, replacing it with a DNS-based tree walk method that is more predictable and self-contained. Receivers walk up the DNS hierarchy and domain owners declare their own boundaries with the psd= tag. The answer lives in DNS, not in a file someone has to remember to update.

Percentage rollout was unreliable. The pct= tag was meant to let domain owners gradually enforce their policy on a percentage of failing mail. In practice, receivers implemented it inconsistently:

  • Some honored it exactly
  • Some rounded
  • Some ignored it entirely

A domain owner setting pct=50 had no reliable way to predict what would happen. DMARCbis replaces this with t=y, a simple binary: you are either testing or you are enforcing. No ambiguity.

Parsing rules were too loose. RFC 7489 was lenient about record syntax. Some receivers accepted malformed records that others rejected, which meant the same DMARC record could produce different results depending on who was reading it. DMARCbis tightens parsing so that a valid record is valid everywhere and a broken record fails everywhere.

The standard needed real authority. As an Informational RFC, DMARC was technically a suggestion. Vendors could implement it however they saw fit, and they did. Promoting DMARC to Standards Track gives the specification formal weight and sets clearer expectations for how receivers should behave.

External Report Authorization

If your rua= or ruf= tag points to a domain you do not own (for example, a third-party reporting service), the destination domain must publish an authorization record. For a DMARC record on example.com with rua=mailto:dmarc@thirdparty.com, the authorization record would be:

example.com._report._dmarc.thirdparty.com IN TXT "v=DMARC1"

This authorizes thirdparty.com to receive reports on behalf of example.com. Without this record, receivers will not send reports to the external destination. This is a common deployment stumble.

New Tags Explained

np= NEW in DMARCbis

Non-Existent Subdomain Policy. This tag controls what happens when someone sends email from a subdomain that does not exist in DNS, like secure-login.yourdomain.com or invoice.yourdomain.com. Attackers prefer non-existent subdomains because they look legitimate and most organizations do not realize they need protection for domains that are not real.

Values: none, quarantine, reject. Policy for non-existent subdomains follows a defined fallback chain:

  • np= (if present) takes precedence
  • If np= is absent, sp= applies
  • If sp= is also absent, p= is used

This hierarchy allows administrators to set a strict reject policy for non-existent subdomains (via np=reject) while maintaining a more permissive policy for legitimate subdomains (via sp=none or sp=quarantine).

Before adding np=reject, review whether any third-party services send mail from dynamically generated subdomains on your behalf. An np=reject policy applies to all non-existent subdomains without exception.

psd= NEW in DMARCbis

Public Suffix Domain indicator. Declares whether a domain is a Public Suffix Domain (like .com, .co.uk, or .gov.au) so the DNS tree walk knows where to stop.

Three values:

  • psd=y means the domain is a PSD and subdomains should be treated as separate organizational domains
  • psd=n means the domain is not a PSD and is the organizational domain for itself and its subdomains (the walk stops here)
  • psd=u (the default when the tag is absent) means the domain has not declared whether it is a public suffix

When psd=u is in effect, the tree walk continues upward to find a domain that explicitly declares psd=y or psd=n. If neither is found within up to 8 tree walk queries plus the initial Author Domain lookup (9 DNS queries maximum), DMARC does not apply.

Most domains should use psd=n. Only operators of actual public suffixes (registries, ccTLDs) should use psd=y. If you are unsure, psd=n is almost certainly correct for your domain.

t= NEW in DMARCbis

Test mode flag. Replaces the deprecated pct= tag. When t=y is set, the domain owner signals that they are testing their policy. Receivers should apply special handling rather than enforcing the stated policy on failing messages.

The key difference from pct=: the old percentage tag told receivers to apply the full policy to a random sample of failing mail. Receivers implemented this inconsistently, with some ignoring it entirely and others interpreting the percentage differently. The binary t= flag removes that ambiguity. Either you are testing (t=y) or you are enforcing (t=n, or omit the tag).

When t= is absent or set to n, the published policy applies as stated.

Deprecated Tags

pct= DEPRECATED

Replaced by the t= tag. In practice, only values of 0 and 100 were reliably honored. Intermediate values like pct=50 produced unpredictable behavior because receivers implemented percentage sampling differently. If your record includes pct=, remove it. Use t=y if you need test mode, or omit the tag entirely for full enforcement.

rf= DEPRECATED

Report format. Only afrf (Authentication Failure Reporting Format) was ever implemented by any receiver. The tag served no practical purpose and can be safely removed.

ri= DEPRECATED

Reporting interval. Receivers rarely respected custom intervals. DMARCbis standardizes on daily aggregate reports. Safe to remove.

The DNS Tree Walk

Under RFC 7489, DMARC policy discovery checked exactly two locations: the exact domain and the organizational domain (determined by the Public Suffix List). If you queried DMARC for news.marketing.example.com, the resolver would check _dmarc.news.marketing.example.com and _dmarc.example.com. Nothing in between.

DMARCbis replaces this with a DNS Tree Walk. Starting at the exact domain, the resolver walks up the DNS hierarchy one label at a time, querying for a DMARC record at each level:

_dmarc.news.marketing.example.com No record
_dmarc.marketing.example.com No record
_dmarc.example.com Record found
_dmarc.com Stopped (psd=n at example.com)

Concrete Example: mail.sales.eu.example.com

_dmarc.mail.sales.eu.example.com No record
_dmarc.sales.eu.example.com No record
_dmarc.eu.example.com No record
_dmarc.example.com Policy found here

The lookup moves up the DNS hierarchy one label at a time until a DMARC record is found or the query limit (8 tree walk queries) is reached.

Organizational Domain

The organizational domain is the base domain where DMARC policy ultimately applies if no subdomain-specific policy exists. It defines both alignment boundaries and the fallback policy location. Under DMARCbis, this is discovered via the DNS tree walk rather than the Public Suffix List.

The first record found becomes the effective policy. The walk stops when it hits a domain with psd=y or psd=n, or after up to 8 tree walk queries plus the initial Author Domain lookup (9 DNS queries maximum), a safety limit to prevent abuse from deeply nested domain names.

If no DMARC record is found after up to 8 tree walk queries (plus the initial Author Domain lookup), or if the walk reaches the DNS root without encountering a record with psd=y or psd=n, DMARC evaluation concludes that no policy applies. The domain is treated as having no DMARC record, and receivers apply their default handling.

This matters because a DMARC record published at an intermediate level, like _dmarc.marketing.example.com, is discovered by DMARCbis but invisible to RFC 7489. During the transition period where some receivers use the old algorithm and some use the new one, the same domain can have different effective policies depending on which standard the receiver implements.

What This Means for Your Domain

The changes in DMARCbis are backward-compatible. Your existing DMARC record with v=DMARC1 will continue to work. But there are things worth reviewing, and what matters depends on your specific configuration.

The simplest approach: run an audit on your domain. The results include a DMARCbis readiness assessment that checks your record against the updated specification and flags exactly what applies to you.

The short version

For most domains, the key changes are:

  • Remove pct=, rf=, and ri= if present. These tags are deprecated and will be ignored.
  • Add np=reject if you already enforce p=reject and want to close the non-existent subdomain loophole
  • Add psd=n to declare that your domain is not a public suffix
  • Confirm that all rua= and ruf= URIs include the mailto: prefix. Bare email addresses are no longer accepted.

A word of caution on np=: this tag applies to all non-existent subdomains. If you use services that send email from dynamically created subdomains, or if marketing teams spin up campaign-specific subdomains without creating DNS records first, an np=reject policy will cause that mail to fail DMARC. Audit your sending infrastructure before adding this tag.

Test your domain's current DMARC configuration to see where you stand, or review the scoring methodology for details on how each protocol is evaluated.

An example of a DMARCbis-compliant record:

v=DMARC1; p=reject; sp=reject; np=reject; psd=n; fo=1; rua=mailto:dmarc@yourdomain.com

Do You Need to Change Anything?

Existing DMARC records (v=DMARC1) continue to work without modification. No immediate action is required. Publication as an RFC is expected in 2026. Organizations should begin reviewing their DMARC configurations for DMARCbis compatibility now, as the transition period will begin once the RFC is published.

To prepare for DMARCbis:

  • Ensure your root domain has a DMARC record
  • Verify subdomain policies are intentional (not relying on PSL edge cases)
  • Consider adding np= to protect non-existent subdomains
  • Consider declaring psd=n explicitly if you are not a public suffix
  • Use dns-audit.com to check your DMARCbis readiness score

Key Takeaways

  • DMARCbis does not change SPF or DKIM validation
  • It improves how receivers discover and apply DMARC policies
  • It removes the dependency on the Public Suffix List
  • Existing records continue to work, with no breaking changes
  • Early preparation (np=, psd=, removing deprecated tags) positions you ahead of adoption
