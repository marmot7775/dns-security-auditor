DKIM2: Per-Hop Signatures and Message Chain of Custody

DKIM2 is a proposed successor to DKIM (RFC 6376). It adds per-hop signatures that form a verifiable chain of custody as a message traverses Signers, Forwarders, Revisers, and Verifiers. As of April 2026 it exists only as IETF drafts. No production deployments exist.

What is DKIM2?

DKIM2 is an IETF draft protocol positioned as the successor to DKIM (RFC 6376). Where DKIM attaches a single originator signature intended to survive delivery, DKIM2 requires every participant in the handling chain to add its own signature. The result is an ordered sequence of signatures that receivers can walk to reconstruct exactly which intermediaries touched the message and in what order.

The effort is led by engineers with deep operational exposure to large mail systems: Bron Gondwana (Fastmail), Richard Clayton (Yahoo), and Wei Chuang (Google). The IETF DKIM working group has adopted the motivation draft, formalizing DKIM2 as a working group item. The core specification and DNS record format are progressing as individual drafts and have not yet been adopted by the working group or published as an RFC.

DKIM2 defines four participant roles: Signers (originating domains that produce the first signature), Forwarders (intermediaries that pass a message along, sometimes to a new recipient, and add a signature in transit), Revisers (intermediaries that modify the message body or headers, such as mailing list managers, and declare the modification), and Verifiers (final receivers that walk the signature chain and evaluate the result).

Why DKIM2 Matters

DKIM (RFC 6376) and ARC (RFC 8617) together cover much of today's email authentication surface, but four classes of problem remain. DKIM2 is designed to address each at the protocol layer rather than through reputation systems or receiver heuristics.

Replay Attacks

A DKIM1 signature is valid for as long as the signing key is published. An attacker who obtains a single legitimately signed message can resend it to millions of new recipients, and each copy verifies because the signature does not bind the message to its intended recipients or delivery context. Receivers see an authentic signature from a reputable domain and deliver the message. DKIM2 binds each signature to the envelope recipient through the rt= tag, so replaying the same signed message to a different address produces a signature that does not verify.

Broken Forwarding

Mailing lists, forwarders, and transformation gateways routinely alter subject lines, prepend footers, or rewrite bodies for archival. Any such change invalidates the originator DKIM1 signature. ARC preserves authentication results across these hops, but the protected artifact is a record of prior verification rather than the message itself. DKIM2 asks each hop to re-sign what it is forwarding, declaring any modifications it made, so a Verifier reconstructs the full handling path from signatures over the actual content that passed each hop.

Backscatter

Message systems frequently generate Delivery Status Notifications (DSNs) in response to undeliverable mail. When a spam campaign forges the Return-Path, those DSNs flood innocent mailboxes whose addresses were spoofed into the envelope. DKIM2's envelope binding and per-hop chain allow a receiver to determine whether the original message legitimately carried the claimed envelope sender, turning backscatter from an unsolvable abuse pattern into something receivers can reject with confidence.

Chain of Custody Visibility

When a forwarded message is modified in transit, current protocols offer little insight into who made which change. ARC attests to authentication state but not to content transformation. DKIM2 sequence numbering combined with the MailVersion header allows a Verifier to see that a message passed through three intermediaries, which one altered the body, and whether each hop was authorized to do so. The chain is cryptographic, not advisory.

Key Differences from DKIM1

Feature DKIM1 (RFC 6376) DKIM2 (draft)
Signatures per message One originator signature (additional signatures permitted but not expected) One signature per hop, added by every participant in the handling chain
Sequence numbering None i=1, i=2, i=3, incremented as the message hops
Envelope binding Not part of the signed data rt= tag binds the signature to the RcptTo address, blocking replay to other mailboxes
Body modification tracking Any body change invalidates the signature MailVersion headers declare modifications made by each Reviser, preserving a verifiable record
Forwarding model Signature survives unchanged or breaks Forwarders and Revisers re-sign, extending the chain
Algorithm posture RSA and Ed25519 Post-quantum signature algorithms anticipated in the design
DNS record format selector._domainkey.example.com New format defined in draft-chuang-dkim2-dns, distinct from DKIM1 records

None of these features are available in production today. The table describes the intent of the current drafts and is subject to change as working group review progresses.

Why There Is No Version Number (and No DKIM3)

The DKIM2 specification deliberately omits a version tag on the DKIM2-Signature header. The authors note in draft-clayton-dkim2-spec that experience since the Internet Message Format standard has shown it is essentially impossible to change protocol version numbers gracefully in deployed email systems. Intermediaries do not uniformly upgrade, and legacy verifiers handle unknown version numbers inconsistently. Rather than repeat that failure mode, DKIM2 treats the header name itself as the version identifier.

If a future incompatible change to DKIM2 ever becomes necessary, the plan is to introduce an entirely new header field name (DKIM3-Signature) rather than bump a version tag. The header name is what Signers, Forwarders, Revisers, and Verifiers look for, so a new name is the cleanest way to signal a protocol break while leaving existing DKIM2 deployments undisturbed.

As of April 2026 there is no DKIM3 draft, working group effort, or proposed specification. Anyone mentioning "DKIM3" today is either speculating about a far-future possibility or confused about terminology. The working group's current focus is getting DKIM2 itself to Last Call.

What Operators Should Do Now

The short answer: nothing that touches deployment. DKIM2 infrastructure does not exist. No signing library will emit DKIM2 signatures, no MTA will verify them, and no receiver will weight them in its reputation model. The useful work is preparation, not publication.

  • Do nothing deployment-wise for DKIM2. Publishing a DKIM2 DNS record today would serve no purpose and could be misinterpreted by tooling that encounters an unknown record format.
  • Track the IETF DKIM working group at datatracker.ietf.org/wg/dkim/. Working group adoption of the core spec will be the first concrete signal that vendor implementation work is approaching.
  • Keep DKIM1 healthy. Audit every selector you publish. Keys should be 2048-bit RSA at minimum. 1024-bit keys fall below the NIST SP 800-131A minimum key strength in effect since 2014 and should be rotated to 2048-bit.
  • Rotate DKIM1 keys on a documented schedule. Quarterly rotation is a reasonable default. Automated rotation with overlap windows avoids selector churn that breaks in-flight mail.
  • Maintain strong DMARC and SPF alignment today. DKIM2 does not replace DMARC or SPF. The authentication stack you build now will carry forward into any DKIM2 transition.

When DKIM2 is closer to deployment, dns-audit.com will add coverage. Until then, the DKIM1 checks on the main audit page reflect what receivers actually evaluate.
