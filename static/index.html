DMARC is the policy layer for email authentication. It tells receiving servers exactly what to do when a message fails verification. In late 2024, the IETF published RFC 9716, officially moving DMARC from an Informational document (RFC 7489) to a Proposed Standard. This audit validates your domain against the current standard.

How DMARC Works: Three Requirements

For a message to pass DMARC, it must satisfy all three of these requirements. If any one fails, the DMARC policy determines what happens to the message.

1. Authentication: Does SPF or DKIM pass?
The message must pass at least one of SPF (sender IP is authorized) or DKIM (cryptographic signature is valid). Both can pass, but only one is required. DKIM is the more reliable mechanism because SPF breaks when email is forwarded through intermediaries (mailing lists, forwarding rules, etc.).
2. Alignment: Does the authenticated domain match the From address?
Passing SPF or DKIM is not enough on its own. The domain that passed the check must also align with the domain in the message's visible "From" address. For example, if a message is sent from user@example.com but SPF passes for esp-provider.com, that is an SPF pass without alignment. The message would need DKIM signed by example.com to achieve alignment.
3. Policy: What happens when authentication or alignment fails?
The domain owner publishes a policy telling receivers what to do with failures. p=none requests no action (monitoring only, useful for collecting aggregate report data). p=quarantine requests that failures be routed to the spam folder. p=reject requests that failures be rejected outright. The policy is a request, not a guarantee. Most mailbox providers honor it.

New Tags in RFC 9716

t=y (Test Mode)
Drops the effective policy by one level. A p=reject record with t=y is treated as p=quarantine. Useful for cautious deployment of a new enforcement policy.
np= (Non-Existent Subdomain Policy)
Sets policy specifically for subdomains that do not exist in DNS. Prevents abuse of made-up subdomains (e.g., fake.example.com).
psd= (Public Suffix Domain)
Signals whether a domain is a Public Suffix (like .gov.uk or .com). Clarifies the organizational boundary for policy discovery.

Adoption Status

RFC 9716 is the authoritative standard, but the transition is ongoing. Major providers (Gmail, Outlook, Yahoo) currently prioritize RFC 9716 features where available but maintain backward compatibility with legacy records. The tree walk, np=, and t= tags may not be honored by all receivers yet. Where this matters, the audit results include a note about adoption.
