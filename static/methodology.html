Methodology

How this tool works, what it checks, and what it cannot check. We believe transparency about methodology is as important as the results themselves.

How We Query DNS

All checks are performed by querying public DNS records from a single server location (DigitalOcean, US-East). Results reflect what our resolver sees at the time of the audit. DNS is distributed by design, so results may vary by resolver, geography, and caching state.

This audit represents a point-in-time snapshot from one vantage point. It does not guarantee global consistency of DNS responses.

What We Check

CheckWhat We DoStandard
DMARC Query _dmarc.domain TXT record. Parse policy, reporting, alignment, and subdomain tags. Perform DMARCbis tree walk for subdomains. Validate syntax, detect deprecated tags (pct, ri, rf). DMARCbis
SPF Query domain TXT records for v=spf1. Recursively resolve all includes to count total DNS lookups. Detect multiple records, void lookups, deprecated mechanisms. RFC 7208
DKIM Query common selectors at selector._domainkey.domain. Analyze key type and strength. Use SPF-based vendor detection to prioritize relevant selectors. RFC 6376
MX Query MX records. Verify each host resolves. Detect null MX (RFC 7505). Identify mail providers. RFC 5321
MTA-STS Query _mta-sts.domain TXT record. Check for hosted policy file. Validate policy mode (enforce, testing, none). RFC 8461
TLS-RPT Query _smtp._tls.domain TXT record. Validate reporting destinations. RFC 8460
BIMI Query default._bimi.domain TXT record. Validate SVG logo URL and profile. Check for VMC/CMC certificate reference. Draft (BIMI Working Group)
DNSSEC Query DNSKEY records. Verify DS record at parent zone. Validate chain of trust (DS digest matches DNSKEY). Check algorithm currency. RFC 4033/4034/4035
CAA Query CAA records. Identify authorized CAs, wildcard policy, and violation reporting (iodef). RFC 8659
DANE Query TLSA records for MX hosts at _25._tcp.mx-host. Verify DNSSEC is present (required for DANE). RFC 7672
Nameservers Query NS records. Test each for authoritative response, resolution, SOA serial consistency, network diversity, IPv6 support.
CT Query crt.sh for Certificate Transparency log entries. Identify active certificates, issuers, wildcards, expiring certs, CAA mismatches. RFC 6962
Blocklist Query Spamhaus DBL for domain-based blocklist status.

What We Cannot Check

This is a DNS-based audit. We query public DNS records only. We do not send or receive email, which means:

  • DKIM signature verification: We detect public keys in DNS but cannot verify that outgoing messages are actually signed or that signatures are valid.
  • DMARC alignment on live mail: Alignment requires comparing the From header with SPF/DKIM domains on a real message. We can only check that the prerequisites exist.
  • Deliverability: Inbox placement depends on reputation, content, engagement, and other factors beyond DNS configuration.
  • DKIM selectors: DKIM selectors are private and cannot be enumerated. We test common selectors but may miss custom ones. A "not detected" result does not mean DKIM is not configured.
  • Outbound sending IPs: We check DNS records, not which IPs actually send mail for your domain. IP reputation is not assessed.
  • Global DNS consistency: Results come from one resolver location. DNS responses may differ in other regions due to GeoDNS, CDN routing, or propagation delays.

Scoring

The security grade (A through F) is a weighted summary across six categories:

CategoryWeightWhat It Measures
DMARC25 pointsPolicy strength, reporting, alignment configuration
SPF20 pointsRecord presence, mechanism quality, lookup count
DKIM15 pointsKey presence, key strength, redundancy
Best Practices20 pointsMTA-STS, TLS-RPT, DANE
Key Security10 pointsKey hygiene, rotation, testing mode
Infrastructure10 pointsDNSSEC, CAA, vendor detection
DKIM scoring does not penalize domains where selectors were not detected, because selectors are private and cannot be verified from outside. A domain with undetectable DKIM receives near-full credit in this category.

Authentication Resilience

Beyond pass/fail, we assess how resilient your authentication is to real-world failure scenarios. A domain where both SPF and DKIM are functional has high resilience because either can independently satisfy DMARC. A domain relying on SPF alone has moderate resilience because forwarded mail will fail. A domain with broken SPF and no detected DKIM has low resilience.

Standards Reference

This tool validates against RFC 7489 (the current DMARC standard) and incorporates features from draft-ietf-dmarc-dmarcbis, the forthcoming update approved by the IESG and awaiting final publication. DMARCbis introduces the DNS tree walk for policy discovery, removes the pct/ri/rf tags, and adds the t= (test mode), np= (non-existent subdomain policy), and psd= (public suffix domain) tags. Where DMARCbis behavior differs from RFC 7489, the audit results note the distinction.
