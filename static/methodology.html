Methodology

How this tool works, what it checks, what it cannot check, and how scores are calculated. We believe transparency about methodology is as important as the results themselves.

How We Query DNS

All checks are performed by querying public DNS records from a single server location (DigitalOcean, US-East). Results reflect what our resolver sees at the time of the audit. DNS is distributed by design, so results may vary by resolver, geography, and caching state. This audit represents a point-in-time snapshot from one vantage point. It does not guarantee global consistency of DNS responses.

We resolve records using dnspython against public nameservers. We do not send or receive email, access private systems, or modify any records. The audit is read-only and non-intrusive.

What We Check

Check What We Do Standard
DMARC Query _dmarc.{domain} TXT record. Parse policy (p, sp), reporting URIs (rua, ruf), alignment settings (adkim, aspf), and enforcement options. Discover organizational domain using the Public Suffix List. Validate record syntax and verify external report authorization per Section 7.1. External reporting URIs are verified to prevent unauthorized data collection. RFC 7489
DMARCbis Perform DNS tree walk for policy discovery, replacing the Public Suffix List lookup used by RFC 7489. Detect new tags (t, np, psd) and flag deprecated tags (pct, ri, rf). Results note where behavior differs from RFC 7489. The tree walk eliminates dependency on the Public Suffix List, which is maintained externally and updated on different schedules by different receivers. draft-ietf-dmarc-dmarcbis
SPF Query domain TXT records for v=spf1. Recursively resolve all include and redirect mechanisms. Count total DNS lookups against the 10-lookup limit. Detect void lookups (2-lookup limit). Flag multiple records, deprecated mechanisms (ptr), invalid IPs, and overly broad CIDRs. The 10-lookup limit is strictly enforced. Mechanisms like +all are flagged as dangerous. RFC 7208
DKIM Query common selectors at {selector}._domainkey.{domain}. Analyze key type (RSA/Ed25519) and strength. Use SPF-based vendor detection to prioritize relevant selectors. Support direct lookup of user-supplied selectors. Selectors are private and cannot be enumerated. A "not detected" result does not mean DKIM is absent. RFC 6376
MX Query MX records. Verify each host resolves. Detect null MX (RFC 7505), dangling hosts, and single-host configurations with no failover. Priority ordering and failover readiness are evaluated. Dangling hosts that do not resolve are flagged. RFC 5321
MTA-STS Query _mta-sts.{domain} TXT record. Fetch and parse the HTTPS policy file at /.well-known/mta-sts.txt. Validate mode, MX pattern matching, and max_age. The HTTPS policy file must be served with a valid TLS certificate to be effective. RFC 8461
TLS-RPT Query _smtp._tls.{domain} TXT record. Validate reporting destinations (mailto and HTTPS). Reporting destinations must be deliverable. Without TLS-RPT, encryption failures are invisible. RFC 8460
BIMI Query default._bimi.{domain} TXT record. Check DMARC enforcement prerequisite. Fetch SVG logo and validate Tiny PS profile. Check for VMC certificate tag. BIMI is a brand feature, not a security control. Requires DMARC enforcement. Gmail requires a VMC or CMC for logo display. Draft (BIMI WG)
DNSSEC Query DNSKEY records. Validate DS record at parent zone. Verify DS digest matches DNSKEY (chain of trust). Identify signing algorithm. Signature validity, algorithm strength, and chain-of-trust integrity are all verified. RFC 4033/4034/4035
CAA Query Certificate Authority Authorization records. Check issue, issuewild, and iodef tags. Flag domains with no issuance restrictions. The critical flag is handled. Without CAA, any CA in the world may issue certificates for your domain. RFC 8659
DANE Query TLSA records at _25._tcp.{mx-host} for each MX host. Validate usage, selector, and matching type fields. Verify DNSSEC is enabled (DANE is ineffective without it). DANE requires a validated DNSSEC chain to function. Without DNSSEC, TLSA records provide no security benefit. RFC 7672
Nameservers Query NS records. Check SOA serial consistency, response times, network diversity across /24 ranges, and IPv6 availability. Delegation, glue records, and authority consistency are validated. IPv6 readiness is noted. RFC 1034/1035
CT Query Certificate Transparency logs via crt.sh. Report issuer breakdown, active certificate count, expiring certificates, wildcard usage, and subdomain discovery. CT log coverage may be incomplete. Do not assume full visibility into all issued certificates. RFC 6962
Blocklist Check domain against Spamhaus DBL with return code interpretation (spam, phishing, malware, botnet C&C). Single blocklist source. A clean result here does not guarantee clean reputation across all blocklists.

What We Cannot Check

This is a DNS-based audit. We query public DNS records only. We do not send or receive email, which limits what we can verify.

DKIM signature verification

We detect public keys in DNS but cannot verify that outgoing messages are actually signed or that signatures are valid. That requires inspecting live email headers.

DMARC alignment on live mail

Alignment requires comparing the From header with SPF/DKIM domains on a real message. We can only confirm that the prerequisites exist in DNS, not that alignment succeeds in practice.

DKIM selectors

Selectors are chosen by each mail service and are not publicly enumerable via DNS. We test common selectors but may miss custom ones. A "not detected" result does not mean DKIM is not configured. Provide your selector for a definitive check.

Outbound sending IPs

We check DNS records, not which IPs actually send mail for your domain. IP reputation is not assessed.

Deliverability

Inbox placement depends on reputation, content, engagement, and other factors beyond DNS configuration. A passing audit does not guarantee deliverability.

Global DNS consistency

Results come from one resolver location. DNS responses may differ in other regions due to GeoDNS, CDN routing, or propagation delays.

Scoring

The security grade (A+ through F) is a weighted summary across six categories. Authentication (DMARC, SPF, DKIM) accounts for 60 of 100 points.

Category Weight What It Measures
DMARC 25 Policy strength (p=reject/quarantine/none), pct rollout, reporting (rua/ruf), subdomain policy (sp=), alignment mode (adkim/aspf)
SPF 20 Record presence, all-mechanism qualifier (-all/~all/?all), DNS lookup count vs. the 10-lookup limit, include complexity. ~all receives full credit when DMARC is enforcing
DKIM 15 Key discovery, key count (redundancy), cryptographic strength (RSA 2048+, Ed25519)
Best Practices 20 MTA-STS (5 pts), TLS-RPT (5 pts), DNSSEC (4 pts), DANE (3 pts), CAA (2 pts), nameserver diversity (1 pt)
Key Security 10 DKIM key rotation status, testing mode (t=y) detection, algorithm modernity (SHA-256/Ed25519 vs. legacy)
Vendor Intelligence 10 Email service provider detection confidence and diversity

DKIM selectors are private identifiers chosen by domain administrators. Unlike DMARC and SPF records, which are published at well-known DNS locations, DKIM keys live under selector-specific names that cannot be enumerated from outside. The tool probes common selectors used by major email providers, but security-conscious organizations routinely use non-standard names. When no selectors are detected, full credit is awarded because absence of discoverable keys does not indicate absence of DKIM signing. For a verified assessment, enter your specific selector in the audit form.

DNSSEC, CAA, and nameserver diversity contribute to the Best Practices category (up to 7 of 20 points). Certificate Transparency and Blocklist checks are evaluated and reported but do not contribute to the numeric score.

A broken SPF record (PermError from exceeding the 10-lookup limit) receives zero points in the SPF category regardless of other mechanisms.

SPF ~all (softfail) receives the same credit as -all (hardfail) when the domain has an enforcing DMARC policy (p=quarantine or p=reject), because DMARC enforcement handles unauthorized mail regardless of the SPF qualifier.

DMARC pct values are scored on a sliding scale: 100% receives full credit (5 pts), 75%+ receives 4, 50%+ receives 3, 25%+ receives 2, and values above 0 receive 1. A pct of 0 (enforcement disabled) receives no credit.

Grade Thresholds

  • A+: 90 and above
  • A: 80 to 89
  • B: 65 to 79
  • C: 50 to 64
  • D: 35 to 49
  • F: Below 35

Authentication Resilience

Beyond the numeric score, we assess how resilient your authentication is to real-world failure scenarios. This is a qualitative assessment, not a scored metric.

  • High: Both SPF and DKIM are functional and DMARC is enforcing. Either mechanism can independently satisfy DMARC alignment, so authentication survives both forwarding (where SPF breaks) and content modification (where DKIM breaks).
  • Moderate: SPF is functional and DMARC is enforcing, but DKIM could not be confirmed. DKIM may exist but was not detectable. Also applies when DKIM is functional but SPF is broken, or when DMARC is not yet enforcing.
  • Low: Broken SPF and no detected DKIM, or no DMARC record at all. The domain has minimal protection against spoofing.

Standards Reference

This tool validates against the following specifications:

DMARC (RFC 7489) Domain-based Message Authentication, Reporting, and Conformance. The current DMARC standard, published in 2015. Defines email authentication policy discovery using the Public Suffix List, SPF and DKIM alignment checking, and aggregate and failure reporting. The foundation of email authentication policy, deployed by the majority of receivers.
DMARCbis (draft-ietf-dmarc-dmarcbis) The in-progress update to DMARC, advancing through the IETF standards process. Replaces the Public Suffix List with a DNS tree walk for organizational domain discovery, which eliminates the dependency on an externally maintained list that receivers updated on different schedules. Introduces new tags (t, np, psd) and deprecates several tags (pct, ri, rf). Where DMARCbis behavior differs from RFC 7489, the audit results note the difference and show both interpretations, helping administrators prepare for the transition.
RFC 7208 Sender Policy Framework (SPF). 10-lookup limit, void lookup limit, mechanism evaluation.
RFC 6376 DomainKeys Identified Mail (DKIM). Key record format, selector resolution, signature semantics.
RFC 8461 MTA Strict Transport Security (MTA-STS). HTTPS-based TLS enforcement for SMTP.
RFC 8460 SMTP TLS Reporting (TLS-RPT). TLS failure reporting for inbound email.
RFC 7672 SMTP Security via DANE (TLSA). DNS-based certificate pinning for mail servers.
RFC 4033/4034/4035 DNS Security Extensions (DNSSEC). Chain-of-trust validation, DNSKEY, and DS records.
RFC 8659 DNS Certification Authority Authorization (CAA). Certificate issuance restrictions.
RFC 6962 Certificate Transparency. Public audit log for issued certificates.
